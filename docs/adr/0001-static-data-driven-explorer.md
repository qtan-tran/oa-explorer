# ADR 0001: A pre-rendered static, data-driven explorer

Status: ACCEPTED (session 1, 2026-11-07). Owner: Quoc-Tan Tran.
Provider-dependent statements verified against official documentation on 2026-11-07; re-verify annually or on any provider announcement (see "Maintenance of this decision").

## Context

ROARA maintains a purposive corpus of OA/OS policies (Germany populated: 412 screened institutions, 56-column schema; five countries planned) and wants a durable, free, accessible explorer with filter/search/record/comparison/download, private local review, and publication only by explicit authorization. Constraints: zero-server preference, no paid services or runtime AI for core operation, WCAG 2.2 AA, machine-readable versioned exports, ten-year portability with no guaranteed provider or dependency.

Data volume is tiny by web standards: the full DE corpus is a 269 KB CSV; even at 10,000 records across many countries, exports remain a few MB. The workload is read-only browsing; updates are batched research releases, not live transactions.

## Decision

Build a **pre-rendered static site generated by a small Python (Jinja2) site generator** consuming a **validated, version-controlled public data export** (CSV of record + JSON view + pre-built search index). Publish, when authorized, on **GitHub Pages** from the public repo (`oa-explorer`). The repository is public and contains only code and documentation; the detailed research ledger and any unpublished data stay in local, gitignored working copies or institutional storage, never inside the repository.

**Why Python + Jinja2 specifically:** the corpus team's existing toolchain is Python/pandas (validate_schema.py, build_combined.py); one language ecosystem minimizes maintainer load; Jinja2 is mature, dependency-light, and template output is plain HTML we control fully. The generator is expected to be a few hundred lines: entity pages, list pages per country/issuer/function, comparison pages, SVG charts with data tables, sitemap/deep links, one optional small vanilla-JS file enhancing the pre-rendered list with client-side filtering over the pre-built JSON index. Without JavaScript the site remains fully usable (each record page is a static deep link).

**Charts and comparisons:** pre-rendered SVG at build time (role="img", title/desc, adjacent data tables). Every chart states its denominator and limitations in adjacent text: e.g., "n = 125 own-coded policies out of 412 screened institutions; counts describe the corpus, not the sector." No composite ranking is ever produced; the ten-dimension profile is shown per dimension (matching the corpus's no-weighted-index commitment).

## Considered alternative: server-backed dynamic app (Flask or Datasette + SQLite)

A serious option for a database-like explorer: always-current data, arbitrary ad-hoc queries, no build step.

Why rejected:
- **Hosting obligation over ten years.** It requires an always-on server: a university server (tied to institutional IT lifespan and project cycles), or a paid host (violates the free-to-use requirement), or a "free" PaaS whose tier may change. A static site needs none; files remain readable even with zero hosting.
- **Archival readability.** With static exports, the archived artifact (CSV/JSON) is the data product; anyone can open it in ten years. A SQLite+app stack makes future readers depend on the app code and a runtime.
- **Operational burden:** patching, uptime, logs, potential login surface — against the explicit zero-server and no-mandatory-login constraints.

Tradeoff accepted by choosing static: no ad-hoc server-side queries and releases required for data updates (acceptable: the corpus updates on research timescales, not real-time). Within the static family we also rejected a client-side SPA (React-style) because hydration adds runtime complexity and dependency churn over ten years and weakens the no-JS resilience we want for accessibility and archival browsing.

## GitHub Pages: fit against current official limits (checked 2026-11-07)

From GitHub's official documentation ([About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)):

- Pages is available **in public repositories with GitHub Free** (and GitHub Free for organizations); private repositories require Pro/Team/Enterprise. → fits; `oa-explorer` is public, so only the Pages-enablement decision remains (M4).
- Usage limits: source repositories have a recommended limit of **1 GB**; published sites may be **no larger than 1 GB**; **soft bandwidth limit 100 GB/month**; **soft limit of 10 builds/hour** (not applicable when publishing via a custom GitHub Actions workflow); deployments time out after 10 minutes; one user/organization site per account (project sites live in a repo folder). → our projected site is < 50 MB even with generous growth; traffic for a research explorer is far below the bandwidth soft limit; deploys happen per release.
- Pages "is not intended for or allowed to be used as a free web-hosting service" for sites "primarily directed at facilitating commercial transactions or providing commercial software as a service (SaaS)", and shouldn't be used for sensitive transactions. → a non-commercial research/education explorer fits the permitted use.
- Visitor IP addresses are logged for security purposes when a Pages site is visited (GitHub Privacy Statement applies). → we state this in the site's privacy note; the site itself collects no data, sets no cookies, and requires no login.

**No claim is made that these free tiers, limits or permissions remain unchanged**; they are date-checked facts, to re-verify annually (maintenance checklist).

**Portable alternative and local preview (documented, tested at M4):** the build output is plain HTML/CSS/JS. It can be served by any static host: university web space, Netlify or Cloudflare Pages free tiers, or locally via `python -m http.server`. Moving host is a copy operation plus DNS update; no code change.

| Data archival DOI (Zenodo or equivalent) | €0 | free public repository; availability assumed, not guaranteed |
| Offline backups | ≈ €0 | institutional storage + existing hardware |
| CI (GitHub Actions, public repo) | €0 | Free plan minutes exceed a seconds-long build |
| Maintainer time | 2–4 h/quarter + ≈ 1 day/year | solo maintainer, steady state after M4 |
| If a private Pages site were ever needed | GitHub Pro ≈ $4/month | avoided by design: review stays local (ledger files are gitignored; the public repo holds only code and docs) |

Ten-year hosting total: ≈ €0–150 plus time. The design's position is that the only truly durable assets are the versioned export files and the static output; everything else is replaceable.

## Consequences and limits

- Interactivity is bounded by what pre-rendering + a small JS enhancement can do; complex multi-facet exploration must stay simple (acceptable for the audience and the cautious-comparison mandate).
- Data updates require a release cycle (validate → export → build → deploy), which is deliberate: it is also the review gate.
- Build tooling still depends on Python and Jinja2; pinned versions, no framework churn, and the generated HTML survives even a total build-tool loss (the site can be re-generated by any future tool from the CSV/JSON exports).
- The public repository raises the publication-discipline requirement: unapproved data must never enter git; enforced by gitignore rules, a pre-commit hook (M1), and permission-filter tests (plan tests 5 and 14).
- Remaining uncertainties: GitHub account plan level (assumed Free); long-term availability of Wayback/ archival snapshots for dead-link resilience (mitigated, not solved: snapshot requirement per link + quarterly dead-link reports); whether the corpus team ratifies the proposed public-field allowlist; Zenodo continuity.

## Maintenance of this decision

Re-verify the provider statements above whenever GitHub, Zenodo or archive.org announce changes, and at least annually (plan §8). If a limit or permission stops fitting, the documented portable-alternative path (any static host) applies; the ADR is then revised with a new date-checked section.
